# U3：升级改成"先落盘再切换" —— 设计与上板验证

> 日期：2026-11-07
> 提交：`f5a0a94`（实现）+ release / docs 三次跟进
> 板卡：STM32F103CBT6，Boot 16 KB，App 108 KB，参数区 4 KB
> 原始日志：`stm32/exp/u3_cut.log`；测试脚本 `stm32/exp/u3_install_cut.py`

---

## 1. 一句话

老流程里 PC 直接往内部 Flash 写，**传到一半断电 = App 区半成品 = 只能接电脑救**。
现在整包先写进 W25Q64 暂存区，校验通过才动内部 Flash；
搬运中断电，下次开机自己把暂存区那份装回去，**全程不需要人工干预**。

---

## 2. 老流程的窗口有多大

```
PC ──E<len>──► Boot 立刻擦掉第 0 页      ← 从这一刻起 App 已无效
PC ──D……  ──► 逐页写内部 Flash          ← 20 秒，全程都是窗口
PC ──X<crc>──► 写第 0 页、跳转
```

第 0 页是"App 有效"的唯一判据（只看头两个字）。一旦擦掉，中途任何一次掉电
都只能停在升级模式等人；现场设备不可能这么干。

---

## 3. 新流程

```
PC ──E<len>──► Boot：清暂存头、擦暂存区（27 个扇区，约 1.2 秒）
                 ★ 内部第 0 页不动
PC ──D……  ──► 每页写 W25 暂存区 + 立刻回读比对
PC ──X<crc>──► 整包 CRC 对上
                 ├─ 写"就绪"头（magic 最后补）
                 ├─ 擦内部第 0 页            ← 此刻 App 才变无效
                 ├─ 搬 1..N 页（逐页 擦→写→回读）
                 ├─ Param_OnUpgrade()（image_ok=0）
                 ├─ 写第 0 页（提交点）
                 └─ 清头 → PASS → 跳 App
```

开机时（`Boot/main.c`）：

```
App 无效 ?
  ├─ 暂存头 = READY 且整包 CRC 对 → 自动重装 → 清标志 → 跳 App
  ├─ 否则 → 金副本恢复（原有逻辑）
  └─ 再失败 → 停在升级模式等人
```

---

## 4. 暂存区放在哪

W25Q64 的现有布局（`golden.h:96~156`）：

| 区间 | 用途 |
|---|---|
| `0x000000`~`0x000FFF` | 金副本头 |
| `0x001000`~`0x01BFFF` | 金副本镜像（108 KB） |
| `0x020000`~`0x020FFF` | 元数据（黑名单） |
| `0x030000`~`0x7A0FFF` | 掉卡缓存数据区（旧指针页 + 7616 槽） |
| `0x7A1000`~`0x7A1FFF` | 旧事件指针页（弃用但不许占） |
| `0x7A2000`~`0x7DDFFF` | 掉卡缓存事件槽（960 × 256 B） |
| `0x7DE000` / `0x7DF000` | 事件指针日志 A / B |
| `0x7E0000`~`0x7FEFFF` | **空闲 124 KB（本次用掉前 112 KB）** |
| `0x7FF000`~`0x7FFFFF` | 自检扇区 |

暂存头 `0x7E0000`（独占一个 4 KB 扇区）、镜像 `0x7E1000`（最大 108 KB，到 `0x7FBFFF`）。
**没有搬动任何现有区域**，缓存容量不变，老数据不受影响。

> 2026-11-08 修正：这张表原来把 `0x7A1000`~`0x7FEFFF` 整段写成"空闲"，漏了事件槽和两条指针日志，
> 暂存区因此一度放在 `0x7B0000`（压在事件槽上）。搬到 `0x7E0000` 起，经过见本文 §9。

## 5. 三个关键实现点

### 5.1 有效标志最后写（和参数区同一套思路）

暂存头结构：`magic / size / crc / state`。
写入顺序是"先写其它字段（magic 位置留 `0xFFFFFFFF`），再单独补 magic"。
中途断电 ⇒ magic 没补上 ⇒ 头无效 ⇒ 当没暂存，不会拿半截镜像去装。

### 5.2 搬运第一步就擦第 0 页（这是测出来的坑）

第一版是"先搬 1..N 页，最后擦/写第 0 页"——听起来很像原来的提交点设计，但错了：

- 搬运期间老的第 0 页还在 ⇒ `Boot_IsAppValid()` 判**有效**
- 而 1..N 页已经是新代码 ⇒ **老向量表 + 新代码的混合镜像**
- 下次开机判"有效"直接跳进去，比停在升级模式糟得多

改成搬运第一件事就擦第 0 页：App 立刻无效，中途断电必然命中"App 无效"分支，
由暂存区或金副本救回来。

> 这个坑只在"装到一半断电"这一条路径上才会暴露。只测"传输中断电"是测不出来的。

### 5.3 自愈只在"App 无效"时才做

`Up_RecoverFromStage()` 会读 108 KB 算 CRC（软件 SPI 约 1.7 秒），
正常开机动不动就跑一遍是不可接受的。所以只在 `Boot_IsAppValid() == 0` 时调用；
用户按住按键（明确要进升级模式）时也不抢。

## 6. 实测（两项）

### 6.1 传输中断电：旧固件不受影响

发 20 KB（约 160 页里的 20 页）后不发 `X`，然后发 `C`：

```
RX[1] C
BOOT: cancel requested -> checking App...
BOOT: upgrade flag cleared
BOOT: app valid -> jumping          ← 老流程这里会是 App INVALID
=== boot ===
APP: ver 74 (2026-11-05 dsh: SD slow-write forensics)
```

判据：`app valid -> jumping`。老流程在同一位置必然打印
`BOOT: but App is INVALID -> stay in upgrade mode`。

> ⚠️ 这一项的第一次测试被 `flags=01`（`U` 请求）干扰了：带标志时 Boot 直接进升级模式，
> 看不出 App 到底有没有效。用 `C` 清掉标志后才是有意义的判据。

### 6.2 装到一半断电：自动装回

发完 `X`、等 1.2 秒（搬运进行中）、用 ST-Link 复位（等效于断电），下次开机的串口：

```
=== BOOT ===
PARAM: img=1 boot=0 seq=37 flags=01
G: stage found -> verify
G: stage ok -> installing
G: stage installed -> retry boot
BOOT: app valid -> jumping
=== boot ===
APP: ver 74 (2026-11-05 dsh: SD slow-write forensics)
```

**没有接电脑，没有人工干预**，从"App 无效"自己恢复成可开机状态。

### 6.3 副作用检查

- Boot 体积：9,072 → **10,616 B**（16 KB 区余 5.4 KB），bin 10,960 B；
- 一次升级耗时：传输 ~20 s（3.5 KB/s，受 115200 停等限制）+ 搬运 ~5 s；
- 稳态采集：`drop=0`，`qmax=1`。

> ⚠️ 这里原本写着"没有观测到抖动"，那是**短窗口**（70 秒）的结论。
> 板子连续跑 2 小时后按 4056 个间隔统计，只有 94.6% 是 100 ms：
>
> | 间隔 | 次数 |
> |---|---|
> | 100 ms | 3835 |
> | 85~99 ms | 108 |
> | 101~115 ms | 113 |
>
> 偏离成对出现（115 后跟 85），平均节拍不变、`drop=0`，但确实是抖动。
> 根因不在 U3，而在上午的 BMP280 修复：整段读取 15~16 ms 全在 `s_i2c_lock` 里，
> 每秒挡 ACQ 一次（`i2c_max` 从 1.5 ms 涨到 16.3 ms 就是这个）。
>
> 已改成"触发 / 取数"两段锁，等转换的 25 ms 用 `vTaskDelay` 不持锁（提交 `0f83321`）。
> 修后：`i2c_max` 回到 1516 µs，2110 个间隔**全部**是 100 ms。

## 6.4 矩阵实验发现的缺口：传输阶段断线后不会自己恢复（2026-11-08）

按不同阶段注入复位，六个点各跑一次：

| 注入点 | 修复前的结果 |
|---|---|
| A 传输 30% | 停在升级模式 → 必须发 `C` 才启动旧固件 |
| B 传输 60% | 同上 |
| C 传输 90% | 同上 |
| D 刚发完 X | **自愈重装**（`G: stage ok -> installing`） |
| E 搬运中 2.5s | **自愈重装** |
| F PASS 后 0.5s | 新固件正常试用 |

搬运阶段确实自恢复了，但**传输阶段不会**：内部 Flash 虽然一个字节都没动，
可是 `U` 设的升级标志只有"升级成功"或 `C` 才清 ⇒ Boot 一直停在升级模式等 PC。
现场无人值守的话，这就等于设备不再工作。

**修复**：升级模式里空闲 30 秒（15 次心跳），且满足三条 —— App 仍有效、
暂存区没有"就绪"镜像、当前在 IDLE —— 就清标志跳回 App。
三条缺一不可：App 无效说明可能装了一半；有就绪镜像说明该走自愈；在 RECV 说明还在收数据。

**验证**（09:46:36）：

```
BOOT: upgrade mode - E<size> / D<seq><hex> / X<crc>
WAIT × 15
BOOT: idle, app still valid -> cancel & boot
=== boot ===
APP: ver 74 ...
```

另跑一次端到端：传 30% → 复位 → 25 秒后自己跳回 App，全程无人工。

> ⚠️ 副作用：如果 PC 在传输中途停顿超过 30 秒，升级会被取消（需要重来）。
> 这个场景没实测，但从逻辑上一定如此。

## 7. 边界（不能说的）
- 两项测试都是**手工注入各一次**，不是概率实验；给不出"断电不会砖"的概率；
- 断电是用 **ST-Link 复位**模拟的，不是真的拔电源——Flash 时序等价，但没有覆盖
  "电源缓慢跌落导致半页写入"这种情形；
- 只测了"装到一半"这一个时间点；没有在搬运的每个页号上都试过；
- 暂存区的 CRC 校验要读 108 KB（约 1.7 秒），**这 1.7 秒里再断电**会重来一遍，
  理论上会拖慢恢复，但没有实测过反复断电；
- W25 若损坏，自愈路径直接失效，只能靠金副本或人工——W25 本身没有冗余。

## 8. 复现方法

```powershell
# 1) 传输中断电（不需要外部工具）
python flash_app.py --stage data --limit 20000
#    然后发 C（或复位），看是不是 app valid -> jumping

# 2) 装到一半断电
python C:\Users\acnkx\Desktop\stm32\exp\u3_install_cut.py
#    脚本自己发 U/E/D/X，X 之后 1.2 秒用 ST-Link 复位，再把开机日志抄回来
```

判据：第 ② 项必须出现 `G: stage ok -> installing` 和 `G: stage installed -> retry boot`；
只出现 `G: stage found` 而没有 `installing`，说明 CRC 校验没过，要查暂存区。

## 9. 回查发现：暂存区原来压在事件槽上（2026-11-08 修）

**事实**：把 U3 的地址和 `golden.c:330` 那张 W25 总图逐行对一遍，
原来定的 `0x7B0000`（头）/ `0x7B1000`（镜像）**落在事件槽 `0x7A2000`~`0x7DDFFF` 里面**。

**当时的推断错在哪**：只看到 `golden.h:110` 写的"数据槽到 `0x7A0FFF` 结束"，
就认定后面 "`0x7A1000`~`0x7FEFFF` 是空的"。而同一段注释下面还有三行没读：

| 区间 | 内容 |
|---|---|
| `0x7A1000`~`0x7A1FFF` | 旧事件指针页（已弃用，但不许占） |
| `0x7A2000`~`0x7DDFFF` | 事件槽 960 × 256 B = 240 KB |
| `0x7DE000` / `0x7DF000` | 事件指针日志 A / B |

**后果（按算术推，修复前的现场没留）**：升级入口会预擦
`(108 KB + 4095)/4096 = 27` 个 4 KB 扇区，即从 `0x7B0000` 起 108 KB；
本次镜像 69,956 B ⇒ 实际覆盖 `0x7B0000`~`0x7C2144` ⇒ 约 **296 条**事件槽记录（共 960 条）被抹成 `0xFF`。
事件指针日志在 `0x7DE000` 之上，没被擦 ⇒ 环的读写游标没坏，坏的是那段地址里的记录内容。

**修法**：头 `0x7E0000`，镜像 `0x7E1000`，最大 108 KB 到 `0x7FBFFF`，
距自检扇区 `0x7FF000` 还有 12 KB 余量。`0x7E0000` 是 `golden.c:342` 里标着"124 KB 余量"的起点。

**验证（2026-11-08 10:00）**：
- Boot 重编：Code 11,136 / RO 296 / ZI 5,456，0 Error 0 Warning —— **尺寸没变**（只改了常量）；
- 烧录 → 复位 → `BOOT: no upgrade request -> normal boot` / `app valid -> jumping`；
- 完整升级一次：`E69956` → `E0` → 547 块停等（3.7 KB/s，19 s）→ `X24FD` → `PASS`
  → `BOOT: upgrade OK -> jumping to App` → `APP: ver 74` / `APP: img ver=5 build=20261107`。

**教训**：地址不能靠"谁先结束"往后推，只能照唯一那张总图排；
总图在 `golden.c:330`，不在 `boot_config.h`。这次就是总图更新了、配置文件没跟着更新。

## 10. 第二轮复查（2026-11-08 上午）：又翻出四件事

上一节修完地址之后，把昨天动过的地方（U3/U5/空闲自救/参数区/金副本）整体过了一遍，找到四件：

### 10.1 自愈路径没抬防回滚下限（功能漏写，已修）

`Up_HandleEnd` 里装成功会 `Param_SetMinVer(m.version)`；
但开机自愈 `Up_RecoverFromStage` 里装成功**没有**这一句。

后果：装到一半断电 ⇒ 自愈把 v6 装好 ⇒ 下限还停在 v5 ⇒ 之后 v5 又能装进来。
修法是自愈成功后同样 `Up_FindMeta` + `Param_SetMinVer`（找不到元数据就跳过，镜像已经在跑了，不再多拒一次）。

### 10.2 自愈之后参数记录没重读（隐患，已修）

`Boot/main.c` 开头把参数读进局部 `prm`，自愈里 `Up_InstallFromStage → Param_OnUpgrade()`
**又会写一版新记录**（`image_ok=0`、`seq+1`）。但局部 `prm` 还是开机那份，两处后果：

- 下面"试用计数"用旧 `image_ok` 判断 ⇒ 自愈后的第一轮试用被跳过；
- 那个分支里 `Param_Save(&prm)` 用的是旧 `seq+1`
  ⇒ 和刚写进去那条撞成同一个 `seq`，开机时取 A 还是 B 就看运气。

修法：自愈成功后补一句 `(void)Param_Get(&prm);`。

> 这两条都是"逻辑上说得通、但和另一条路径不一致"，测试跑不出来（v5→v5 时 SetMinVer 直接早退），
> 所以只能算**代码级修正**，没有实测波形。要有 v6 镜像才能看见差异。

### 10.3 两条长循环没喂狗（隐患，已补）

`Up_StageCrc()` 读满 108 KB ≈ 1.7 秒、`Up_InstallFromStage()` 108 页 ≈ 3~5 秒，
整段没有 `BOOT_FEED_IWDG()`；而金副本恢复 `boot_golden.c` 一直是每页喂一次。

今天实测说明这条目前咬不到人：**App 在跑（IWDG 已启）→ ST-Link 复位 → Boot 里读 `IWDG->PR` 仍是 00**，
即 IWDG 外设被系统复位清掉了（这本来就是 `Boot/main.c` 里 probe 那条注释的结论）。
但这是"靠硬件复位行为兜着"，不是设计保证，所以两条循环都补上了喂狗。

### 10.4 文档里的"App 区 = 112 KB"（真雷，已清）

`APP_SIZE` 早就是 108 KB，但还有 **6 个文件里十几处**注释写着 112 KB，其中两处会直接害人：

- `Boot/boot_golden.h`：写"第 1~111 页"（实际是 1~107）；
- `Boot/boot_config.h` 的 W25 布局图：写"`0x010000` 4 KB 元数据"，
  而元数据实际在 `0x020000` —— `0x010000` 正压在金副本镜像的第二块上，
  照那句去写就会擦掉镜像。

现在这十几处统一改成 108 KB / 108 页，并在这张图的注释里加了一句"唯一权威版在 `golden.c:330`"。

### 10.5 复查后的验证

- Boot 重编：Code 11,136 → **11,184 B**（+48 B），bin 11,480 → **11,528 B**，16 KB 区余 4.7 KB；
- 烧录后跑一次"装到一半复位"（`exp/u3_install_cut.py`）：
  `G: stage found -> verify` → `G: stage ok -> installing` → `G: stage installed -> retry boot`
  → `BOOT: app valid -> jumping` → `APP: img ver=5`，自愈链没回归；
- `PARAM: img=1 boot=0 seq=115 flags=01 min=5`：断电那一刻 `Param_OnUpgrade()` 还没执行，
  所以 `flags` 还是 01，自愈装完后由 `Param_OnUpgrade()` 清掉。

### 10.6 复查里"看过但没动"的

- `Up_InstallFromStage` 里第 0 页被擦两次（进函数一次、提交前一次）——多的那 40 ms 换"顺手兜住中途被写脏"，留着；
- `Up_FindMeta` 全镜像扫 `41 54 45 4D`，理论上可能撞上别的字节序列
  —— 后面还有 `version ∈ [1,100000]` 和 `rsv == 0` 两道判别，概率约 1e-5 量级，留着；
- `SD_SPI.c` 的 `SD_INIT_TIMEOUT_MS 3000` 用的是 DWT 毫秒，真的会中止，不是假的；
- `BMP280_Fetch` 失败时只把 `g_press_x10pa` 置 0，`g_bmp_temp_x100` 留着上一次的值
  —— 和 `temp_ds` 的"给无效值"不一致，但温度慢变，影响小，记在这不修。
