# U3：升级改成"先落盘再切换" —— 设计与上板验证

> 日期：2026-11-07
> 提交：`f5a0a94`（实现）+ release / docs 三次跟进
> 板卡：STM32F103CBT6，Boot 16 KB，App 108 KB，参数区 4 KB
> 原始日志：`stm32/exp/u3_cut.log`；测试脚本 `stm32/exp/u3_install_cut.py`

---

## 1. 一句话

老流程里 PC 直接往内部 Flash 写，**传到一半断电 = App 区半成品 = 只能接电脑救**。
现在整包先写进 W25Q64 暂存区，校验通过才动内部 Flash；
搬运中断电，下次开机自己把暂存区那份装回去，**全程不需要人工干预**。

---

## 2. 老流程的窗口有多大

```
PC ──E<len>──► Boot 立刻擦掉第 0 页      ← 从这一刻起 App 已无效
PC ──D……  ──► 逐页写内部 Flash          ← 20 秒，全程都是窗口
PC ──X<crc>──► 写第 0 页、跳转
```

第 0 页是"App 有效"的唯一判据（只看头两个字）。一旦擦掉，中途任何一次掉电
都只能停在升级模式等人；现场设备不可能这么干。

---

## 3. 新流程

```
PC ──E<len>──► Boot：清暂存头、擦暂存区（27 个扇区，约 1.2 秒）
                 ★ 内部第 0 页不动
PC ──D……  ──► 每页写 W25 暂存区 + 立刻回读比对
PC ──X<crc>──► 整包 CRC 对上
                 ├─ 写"就绪"头（magic 最后补）
                 ├─ 擦内部第 0 页            ← 此刻 App 才变无效
                 ├─ 搬 1..N 页（逐页 擦→写→回读）
                 ├─ Param_OnUpgrade()（image_ok=0）
                 ├─ 写第 0 页（提交点）
                 └─ 清头 → PASS → 跳 App
```

开机时（`Boot/main.c`）：

```
App 无效 ?
  ├─ 暂存头 = READY 且整包 CRC 对 → 自动重装 → 清标志 → 跳 App
  ├─ 否则 → 金副本恢复（原有逻辑）
  └─ 再失败 → 停在升级模式等人
```

---

## 4. 暂存区放在哪

W25Q64 的现有布局（`golden.h:96~156`）：

| 区间 | 用途 |
|---|---|
| `0x000000`~`0x000FFF` | 金副本头 |
| `0x001000`~`0x01BFFF` | 金副本镜像（108 KB） |
| `0x020000`~`0x020FFF` | 元数据（黑名单） |
| `0x030000`~`0x7A0FFF` | 掉卡缓存（指针页 + 7616 槽） |
| `0x7A1000`~`0x7FEFFF` | **空闲（本次用掉前 112 KB）** |
| `0x7FF000`~`0x7FFFFF` | 自检扇区 |

暂存头 `0x7B0000`（独占一个 4 KB 扇区）、镜像 `0x7B1000`（108 KB，到 `0x7CC000`）。
**没有搬动任何现有区域**，缓存容量不变，老数据不受影响。

---

## 5. 三个关键实现点

### 5.1 有效标志最后写（和参数区同一套思路）

暂存头结构：`magic / size / crc / state`。
写入顺序是"先写其它字段（magic 位置留 `0xFFFFFFFF`），再单独补 magic"。
中途断电 ⇒ magic 没补上 ⇒ 头无效 ⇒ 当没暂存，不会拿半截镜像去装。

### 5.2 搬运第一步就擦第 0 页（这是测出来的坑）

第一版是"先搬 1..N 页，最后擦/写第 0 页"——听起来很像原来的提交点设计，但错了：

- 搬运期间老的第 0 页还在 ⇒ `Boot_IsAppValid()` 判**有效**
- 而 1..N 页已经是新代码 ⇒ **老向量表 + 新代码的混合镜像**
- 下次开机判"有效"直接跳进去，比停在升级模式糟得多

改成搬运第一件事就擦第 0 页：App 立刻无效，中途断电必然命中"App 无效"分支，
由暂存区或金副本救回来。

> 这个坑只在"装到一半断电"这一条路径上才会暴露。只测"传输中断电"是测不出来的。

### 5.3 自愈只在"App 无效"时才做

`Up_RecoverFromStage()` 会读 108 KB 算 CRC（软件 SPI 约 1.7 秒），
正常开机动不动就跑一遍是不可接受的。所以只在 `Boot_IsAppValid() == 0` 时调用；
用户按住按键（明确要进升级模式）时也不抢。

## 6. 实测（两项）

### 6.1 传输中断电：旧固件不受影响

发 20 KB（约 160 页里的 20 页）后不发 `X`，然后发 `C`：

```
RX[1] C
BOOT: cancel requested -> checking App...
BOOT: upgrade flag cleared
BOOT: app valid -> jumping          ← 老流程这里会是 App INVALID
=== boot ===
APP: ver 74 (2026-11-05 dsh: SD slow-write forensics)
```

判据：`app valid -> jumping`。老流程在同一位置必然打印
`BOOT: but App is INVALID -> stay in upgrade mode`。

> ⚠️ 这一项的第一次测试被 `flags=01`（`U` 请求）干扰了：带标志时 Boot 直接进升级模式，
> 看不出 App 到底有没有效。用 `C` 清掉标志后才是有意义的判据。

### 6.2 装到一半断电：自动装回

发完 `X`、等 1.2 秒（搬运进行中）、用 ST-Link 复位（等效于断电），下次开机的串口：

```
=== BOOT ===
PARAM: img=1 boot=0 seq=37 flags=01
G: stage found -> verify
G: stage ok -> installing
G: stage installed -> retry boot
BOOT: app valid -> jumping
=== boot ===
APP: ver 74 (2026-11-05 dsh: SD slow-write forensics)
```

**没有接电脑，没有人工干预**，从"App 无效"自己恢复成可开机状态。

### 6.3 副作用检查

- Boot 体积：9,072 → **10,616 B**（16 KB 区余 5.4 KB），bin 10,960 B；
- 一次升级耗时：传输 ~20 s（3.5 KB/s，受 115200 停等限制）+ 搬运 ~5 s；
- 稳态采集：`drop=0`，`qmax=1`。

> ⚠️ 这里原本写着"没有观测到抖动"，那是**短窗口**（70 秒）的结论。
> 板子连续跑 2 小时后按 4056 个间隔统计，只有 94.6% 是 100 ms：
>
> | 间隔 | 次数 |
> |---|---|
> | 100 ms | 3835 |
> | 85~99 ms | 108 |
> | 101~115 ms | 113 |
>
> 偏离成对出现（115 后跟 85），平均节拍不变、`drop=0`，但确实是抖动。
> 根因不在 U3，而在上午的 BMP280 修复：整段读取 15~16 ms 全在 `s_i2c_lock` 里，
> 每秒挡 ACQ 一次（`i2c_max` 从 1.5 ms 涨到 16.3 ms 就是这个）。
>
> 已改成"触发 / 取数"两段锁，等转换的 25 ms 用 `vTaskDelay` 不持锁（提交 `0f83321`）。
> 修后：`i2c_max` 回到 1516 µs，2110 个间隔**全部**是 100 ms。

## 6.4 矩阵实验发现的缺口：传输阶段断线后不会自己恢复（2026-11-08）

按不同阶段注入复位，六个点各跑一次：

| 注入点 | 修复前的结果 |
|---|---|
| A 传输 30% | 停在升级模式 → 必须发 `C` 才启动旧固件 |
| B 传输 60% | 同上 |
| C 传输 90% | 同上 |
| D 刚发完 X | **自愈重装**（`G: stage ok -> installing`） |
| E 搬运中 2.5s | **自愈重装** |
| F PASS 后 0.5s | 新固件正常试用 |

搬运阶段确实自恢复了，但**传输阶段不会**：内部 Flash 虽然一个字节都没动，
可是 `U` 设的升级标志只有"升级成功"或 `C` 才清 ⇒ Boot 一直停在升级模式等 PC。
现场无人值守的话，这就等于设备不再工作。

**修复**：升级模式里空闲 30 秒（15 次心跳），且满足三条 —— App 仍有效、
暂存区没有"就绪"镜像、当前在 IDLE —— 就清标志跳回 App。
三条缺一不可：App 无效说明可能装了一半；有就绪镜像说明该走自愈；在 RECV 说明还在收数据。

**验证**（09:46:36）：

```
BOOT: upgrade mode - E<size> / D<seq><hex> / X<crc>
WAIT × 15
BOOT: idle, app still valid -> cancel & boot
=== boot ===
APP: ver 74 ...
```

另跑一次端到端：传 30% → 复位 → 25 秒后自己跳回 App，全程无人工。

> ⚠️ 副作用：如果 PC 在传输中途停顿超过 30 秒，升级会被取消（需要重来）。
> 这个场景没实测，但从逻辑上一定如此。

## 7. 边界（不能说的）
- 两项测试都是**手工注入各一次**，不是概率实验；给不出"断电不会砖"的概率；
- 断电是用 **ST-Link 复位**模拟的，不是真的拔电源——Flash 时序等价，但没有覆盖
  "电源缓慢跌落导致半页写入"这种情形；
- 只测了"装到一半"这一个时间点；没有在搬运的每个页号上都试过；
- 暂存区的 CRC 校验要读 108 KB（约 1.7 秒），**这 1.7 秒里再断电**会重来一遍，
  理论上会拖慢恢复，但没有实测过反复断电；
- W25 若损坏，自愈路径直接失效，只能靠金副本或人工——W25 本身没有冗余。

## 8. 复现方法

```powershell
# 1) 传输中断电（不需要外部工具）
python flash_app.py --stage data --limit 20000
#    然后发 C（或复位），看是不是 app valid -> jumping

# 2) 装到一半断电
python C:\Users\acnkx\Desktop\stm32\exp\u3_install_cut.py
#    脚本自己发 U/E/D/X，X 之后 1.2 秒用 ST-Link 复位，再把开机日志抄回来
```

判据：第 ② 项必须出现 `G: stage ok -> installing` 和 `G: stage installed -> retry boot`；
只出现 `G: stage found` 而没有 `installing`，说明 CRC 校验没过，要查暂存区。
