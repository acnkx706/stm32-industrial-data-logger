# EXP-01 人工观察（脚本算不出来、必须人看的部分）

> 这一页记的是跑账本时**眼睛看到**、但脚本无法自动判断的现象。
> 每一条都带可复核的命令或字段，便于别人当场重现。

## 1. 卡上存在同名目录条目（FAT 层残留）

`E:\26101801.CSV` 在目录里出现两次：

```
2026/10/18  17:21        22,995,040 26101801.CSV
2026/10/18  18:04                 0 26101801.CSV
```

- `ReadAllBytes()` 读到的是 22,995,040 字节那份；
- `cmd /c dir /a` 同时列出两份，合计 2 File(s)。

判断：这是 FAT 目录项残留（很可能是某次 `f_open` 重试留下的空壳条目），
不是两个真实文件。**后果**：按名字遍历的拷贝脚本可能拷到 0 字节那份，
所以 `run_exp01.ps1` 里做了"同名保留最大字节数"的去重。

建议：在 PC 上跑一次 `chkdsk E: /f` 清掉空壳条目后再归档。

## 2. `26101801.CSV` 里那 15 MB 外来数据不是固件写的

**现象**：该文件 22,995,040 字节，但只有前 7,864,320 字节是 CSV（99,002 行），
其余 15,130,720 字节是二进制，能认出 ZIP 本地头和 802 个 24×24 的 PNG 图标。

**五条证据**（`png_probe.py` 可复跑）：

1. **边界正好在簇边界上**：CSV 有效数据结束于 `7,864,320 = 240 × 32 KB`，一字节不差。
2. **最后一行是写到一半被截断的**：
   ```
   前一行完整：75778,7577801,1017080,1792350152,-103,26,2028,...,21666\r\n
   下一行只剩：75779,7577901,1017080,179235015      ← 31 字节，补满 7,864,320 后转二进制
   ```
   说明写入停在这里，后面那 15 MB 从来没有被写过。
3. **目录项长度大于实际写入量**：`size = 22,995,040`，实际写入 `7,864,320`，
   差额 `15,130,720` 正好是外来数据的长度。
4. **外来数据是什么**：ZIP 本地头 `PK\x03\x04` 1,534 个、PNG 签名 802 个、
   IHDR 尺寸全是 24×24；没有 ZIP 中央目录与结尾，是碎片而不是完整压缩包。
5. **全卡唯一**：拿这段数据的前 96 字节在卡上 24 个 CSV 里检索，只有这一个文件命中。

**发生过程**：卡上早先有一个图标包类文件（一堆 24×24 PNG），被删除后簇被回收并分给了
`26101801.CSV`，但**目录项里的长度与簇链没有清干净**，于是这个文件"继承"了旧文件的大小与链。
固件按正常流程写 CSV，只写到第 240 个簇；再往后读，读到的全是旧文件遗留的数据。

**为什么不是固件写坏**：固件只 `sprintf` 出 CSV 文本，没有任何路径产生 PNG/ZIP；
写入量与声明长度差 15 MB；边界精确落在簇边界，而 CSV 行是变长的，自然写不可能刚好停在那里。

**同源现象**：同一个文件名在卡上有两份目录项（22,995,040 与 0 字节），见第 1 节。

**其它早期文件**：`26101901.CSV` 也有约 9 万行外来二进制，但没有 ZIP/PNG 签名，
同时还含 73,966 行重复的表头（说明那个文件当天被反复重建）；
`26101903`、`26101904`、`26102001` 未见大块外来数据。

**对账本的影响**：10-18 ~ 10-20 三天的缺口数字不可比，已排除在第 6 节的对账之外。
`26101801.CSV` 前 7.86 MB 的数据本身是好的，逐行 CRC 通过。

## 3. 采集速率在 10-29 出现台阶

按"每个整天文件的 rows"看（都是 00:00:00 开、24:00:00 收，名义 864,000）：

| 日期 | rows | 与 864,000 的差 |
|---|---:|---:|
| 10-21 | 745,816（半天） | — |
| 10-22 | 858,366 | -5,634 |
| 10-23 | 862,789 | -1,211 |
| 10-24 | 862,435 | -1,565 |
| 10-25 | 861,269 | -2,731 |
| 10-26 | 861,783 | -2,217 |
| 10-27 | 862,450 | -1,550 |
| 10-28 | 862,740 | -1,260 |
| **10-29** | **864,005** | **+5** |
| 10-30 | 864,030 | +30 |
| 10-31 | 863,990 | -10 |
| 11-01 | 864,010 | +10 |
| 11-02 | 864,050 | +50 |

- 10-28 及以前：每天比名义少 1,200 ~ 5,600 行；
- 10-29 起：贴着 0 走（±60 行）。

**同期没有任何代码提交**（`git log --since=2026-10-22 --until=2026-11-02` 为空），
`Clk_CalibOnce()` 只打印 ppm、不写 RTC 分频（`freertos_demo.c:1580-1612`）。

所以这个台阶**不是代码造成的**。目前只有三种可能，全都未验证：

1. 硬件变动（换了晶振/换了板子）；
2. 有一段未提交的固件在 10-29 前后被烧进去过；
3. 我的口径有漏洞（例如那几天文件不是整点开始）。

**验证方法**：掉电保持 RTC，用 PC 对时连续测 24 小时，
直接量 RTC 的绝对偏差；同时在同一台机器上看 `tick` 走 24 小时的毫秒数。

## 4. CRC：最终结果 0 失败

按"至少 15 个字段 + 整行只允许 数字/逗号/减号/小数点"的口径过滤后：

| 项 | 值 |
|---|---:|
| 参与校验的行 | 12,722,572 |
| CRC 失败 | **0** |
| 未参与（旧格式 crc=0） | 196 |
| 被判为非数据行（外来二进制/短行） | 见 `crc_all.csv` 的 `fmt_bad` |

第一版脚本没有做字符集校验，会把"最后一列恰好是数字"的垃圾行当成数据行，
于是报出 32 行 CRC 失败；加上校验后这些行归到 `fmt_bad`，真正的失败数为 0。

## 5. 口径已统一（原记录：两张表 rows 曾差 34 行）

第一版 `crc_all.py` 只做了列数下限，没做字符集校验，比 `manifest_17d.csv` 多算 34 行。
现在两个脚本用同一套规则：**至少 15 个字段，且整行只允许 `0-9 , - .`**，
复跑后两表 rows 完全一致（12,722,768）。

## 6. 16,175 的对账结果

取 **11 个整天文件**（10-22 ~ 11-02，每个都是 00:00:00 开、24:00:00 收）：

```
864,000 × 11 = 9,504,000（名义）
实际数据行     = 9,487,867
差额           = 16,133
README 声称    = 16,175
两者相差       = 42 行（在 ±50 容差内）
```

四块拆分（同一窗口）：

| 块 | 行数 | 说明 |
|---|---:|---|
| 假缺口（tick/rtc 速率差） | **10,095** | 约 63%：不是丢数据，是采集速率与"每天 864,000"这个假设的差 |
| 文件内真缺口 | **2,056** | 约 13%：有 1,730 集中在 10-22（那天有 4 段/重启），其余多为个位数 |
| 其余（rtc 日长不足 + 异常段归属） | **3,982** | rtc 日长不足 4,800 被异常段相抵后的余量，未再细分 |
| 合计 | 16,133 | 与差额自洽 |

**结论**：README 的 16,175 里，**只有约 2,056 行（13%）是真正在文件内缺失的记录**，
其余主要是"tick 时间基与物理秒不同步"造成的假缺口。这与 11-04 夜间的判断方向一致，
但现在有全量账本了，不再是推算。

**注意**：10-18 ~ 10-21 这四天的文件不参与上述对账，原因见第 1、2 条
（介质损坏、格式演进、大量重启），它们的缺口数字不可比。
