# 26101801.CSV 取证：那 15 MB 外来数据是怎么进来的

> 结论等级：**推断**（证据链完整，但没有当时的过程日志，所以不写成"已证实"）
> 复跑：`python png_probe.py _stage\26101801.CSV`
> 外来数据本身**不入库**，只在本文登记计数与偏移。

---

## 一、事实

| 项 | 值 |
|---|---:|
| 文件大小（目录项 size） | 22,995,040 |
| 其中 CSV 有效数据 | **7,864,320 字节**（99,002 行） |
| 外来数据 | **15,130,720 字节** |
| 外来区起始偏移 | 7,864,320 = **240 × 32 KB**（正好簇边界） |
| 外来区里的 ZIP 本地头 `PK\x03\x04` | 1,534 个 |
| 外来区里的 PNG 签名 `\x89PNG\r\n\x1a\n` | 802 个 |
| PNG 的 IHDR 尺寸 | 全部 24 × 24 |
| ZIP 中央目录 / 结尾记录 | 0 |
| 该数据在卡上其它 23 个 CSV 里的命中 | 0 |

## 二、四条判据

**① 边界落在簇边界上**
CSV 有效数据结束于 `7,864,320`，正好是 `240 × 32768`。CSV 行是变长的，
自然写入不可能刚好停在簇边界；停在边界说明"写到第 240 个簇就结束了"。

**② 最后一行的截断形态**
```
75778,7577801,1017080,1792350152,-103,26,2028,1,1,-1,2356,2518,685,1,3894,21666\r\n
75779,7577901,1017080,179235015        ← 只有 31 字节，补满 7,864,320 后转二进制
```
第 31 字节刚好补满簇边界，之后直接是 PNG 签名。

**③ 目录项长度大于实际写入量**

```
size       22,995,040
实际写入    7,864,320
差额       15,130,720   ← 与外来数据长度完全相等
```

**④ 外来数据是"一堆图标"**

ZIP 本地头 1,534 个、PNG 签名 802 个、IHDR 全是 24×24，没有中央目录 ——
是一个压缩包中段的碎片（图标类资源的典型形态），不可能是本固件产生的字节。

## 三、推断的发生过程

1. 卡上早先存在一个图标包类文件（大量 24×24 PNG，装在 ZIP 容器里）；
2. 它被删除后，簇被回收；
3. `26101801.CSV` 的目录项**继承了旧文件的长度与簇链**（同一次目录损坏的另一半，
   就是第 1 节记录的"同名双目录项"）；
4. 固件按正常流程写 CSV，从第 0 簇开始写，写到第 240 簇结束；
5. 再往后读时，链上挂的是旧文件的簇，于是读出了那 15 MB 图标数据。

## 四、为什么不是固件写坏

- 固件只 `sprintf` 出 CSV 文本，没有任何代码路径产生 PNG/ZIP；
- 写入量与声明长度相差 15 MB，而这个差值恰好等于外来数据长度；
- 边界精确落在簇边界，且最后一行被截断在簇边界前 31 字节；
- 同一段数据在卡上其它 23 个文件里检索不到（不是共享缓冲区残留）。

## 五、影响与处置

- **不影响账本结论**：该文件前 7.86 MB 的 99,002 行是真实数据，逐行 CRC 通过；
- **不参与 16,175 的对账**：10-18 ~ 10-20 三天被整体排除（见 `summary_clean11.md` 的口径说明）；
- **建议**：归档前在 PC 上对该卡跑 `chkdsk E: /f`，并且先做整卡镜像再跑（chkdsk 会改动原始证据）；
- **本仓库不含那 15 MB 外来数据**，只保留本文件的计数与偏移，便于复核。
