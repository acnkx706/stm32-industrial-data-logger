## 二、34 vs 24

README 写的 "34 个文件" 与账本的 24 个数据文件不是同一个口径。最接近的还原是：

```
24 个数据文件（含 0 字节的 26101805）
+ 6 个事件文件（范围内）
+ 2 个开发期变体（26102101_16col / _17col）
+ 2 个非正常日期文件（70010101 数据、70010190 事件）
= 34
```

这条还原能对上 34 这个数字，**但它只是数字上的拼合，没有当时的清单可佐证**，
所以标为"未证实"。

## 三、122,171 行

```
README 声称总行数   12,844,939
本账本实测          12,722,768
差                    122,171
```

穷举卡上被排除文件的组合后，**最接近的还原**是：

```
70010101.CSV（RTC 未设，日期 2020-01-01）    117,592
26102101_17col.CSV（开发期 17 列试验）         4,527
                            合计            122,119
                                    残差          52 行
```

也就是说：README 的总数里很可能包含了那个"日期是 2020 年"的文件和一份开发期变体，
但仍差 **52 行未解释**。这 52 行可能是早期版本的行数统计口径差异（例如把表头/空行算了进去）。

**结论：122,171 解释到 122,119，余 52 行标"未解释"，不硬凑。**

## 四、为什么不把早期文件算进 headline

`26101801`、`26101901` 等 10-18 ~ 10-20 的文件存在介质层问题与格式反复：

- 外来数据（ZIP/PNG 碎片，见 `forensics_26101801.md`）；
- `26101901` 含 73,966 行重复表头（当天被反复重建）；
- 多段（最多 486 段）大量重启。

这些文件的行数不代表"链路能力"，把它们算进"每天缺多少行"会把介质问题当成丢行，
所以 headline 只用 10-22 ~ 11-01 这 11 个干净整天文件。
