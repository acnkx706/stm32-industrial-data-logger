# A-真写臂：91.50% 占用 + 真实写 1.48 GB 之后立刻跑 100k

> 时间：2026-11-06 12:46:33 开始写 → 12:49:16 写完 → 12:49:31 安全弹出 → 用户上电
> 固件：`Objects/app_fast100k.bin`（70,288 B，跟占位臂同一个固件，没重烧，靠断电重启触发）
> 原始日志：`realwrite_100k.log`
> 解析产物：`arm_realwrite/latency_summary.csv`、`latency_top.csv`、`latency_hist.csv`

---

## 一、这一臂和占位臂的唯一差别

| 条件 | 占位臂 | 本臂 |
|---|---|---|
| 怎么把卡填到 91.5% | `fsutil file createnew`（瞬间标成已分配，不写数据） | **真实写 1.48 GB 数据**（4 MB 一块，末了 `fsync`） |
| 写入耗时 | 不到 1 秒 | **163.7 秒**（约 9.3 MB/s） |
| 写入后是否刷卷 | `Write-VolumeCache` | `Write-VolumeCache`（一样） |
| 最终占用 | 91.57% | **91.50%** |

**为什么要拆成两臂**：原事件（10:29 那次 942 ms）用的是 `fsutil`，
它只是把 1.5 GB 标成已分配，**并没有真的往闪存里写 1.5 GB**。
所以那次 942 ms 不可能由"写 1.5 GB 造成的卡内 GC"直接解释。
本臂就是把"真的写 1.5 GB"这个变量单独加上去，看 942 ms 会不会出现。

## 二、本臂的实测条件

| 项目 | 数值 |
|---|---:|
| 卷总容量 | 3,956,801,536 B |
| 写完可用 | 336,297,984 B |
| **写完已用** | **91.50%** |
| `FILLER.BIN` | 1,503,955,517 B（真实数据） |
| 写开始 / 写完 | 12:46:33 / 12:49:16 |
| 安全弹出 | 12:49:31 |
| 实际吞吐 | 约 9.3 MB/s |

写之前那一轮（占位臂）让板子写了 51,200,000 B 进去，
所以这轮起始占用是 92.87% 减掉占位文件后约 53.5%，再真写到 91.50%。

## 三、附带验证：板子到底写了多少

占位臂跑完 100,000 个样本后，卡上 `EXP02.BIN` 从 65,375,232 B 涨到 116,575,232 B，
**正好多了 51,200,000 B = 100,000 × 512 B**，一个字节不多不少。

这条比 `f_write` 返回 OK 更有说服力：它证明"报告的样本数"和"卡上真实增长"是对上的。

## 四、时间基准

断电重启后，`Exp02_FastLatRun` 先等 15 秒，然后 mount/open 开始写。
所以"真实写入结束"到"第一个样本"之间存在：弹出(15 s) + 人工换卡 + 上电 + 15 s 延时。
**这一臂的 0 分钟点实际是从约 1~3 分钟开始的**，不是严格 0 分钟。
占位臂同样如此。写报告时必须写"约"，不能写"立即"。

## 五、结果

| 项目 | 数值 |
|---|---|
| `f_write` | n=100,000，平均 **3.64 ms**，max **67.19 ms** |
| `f_sync` | n=100,000，平均 **3.80 ms**，max **51.16 ms** |
| ≥100 ms | **0 次** |
| ≥256 ms | **0 次**（`ovf=0`） |
| 最慢那一笔 | 开机后 42.5 秒（写 67.19 ms）；sync 最快那一笔在 243 秒 |
| 桶和 | write 80,684 / sync 82,057（n=100,000，约 19% 因 `uint16` 饱和丢失，分位数不可引） |

**942 ms 仍然没有复现。**

和占位臂对照（两臂条件只差"fsutil 占位"与"真实写 1.48 GB"）：

| | 占位臂 | 真写臂 | 差 |
|---|---:|---:|---:|
| 占用 | 91.57% | 91.50% | — |
| `f_write` 平均 | 3.63 ms | 3.64 ms | +0.3% |
| `f_write` max | 72.07 ms | 67.19 ms | −7% |
| `f_sync` 平均 | 3.77 ms | 3.80 ms | +0.8% |
| `f_sync` max | 48.93 ms | 51.16 ms | +5% |
| ≥256 ms | 0 | 0 | — |

**真实写 1.48 GB 之后，延迟一点没变差。** 这直接否掉了"持续大批量写会触发卡内 GC 长尾"这条最自然的解释——
至少在这次的条件和这个样本量下没有。

## 六、这一臂最慢那一笔在 42.5 秒，不是第一笔

占位臂最慢的写落在 15.25 秒（mount/open 之后第一笔附近），本臂落在 42.5 秒。
两臂的"首笔慢"现象并不一致，所以**不能把 72 ms 说成冷启动**——
只能说"最坏 72 ms，位置不稳定"。冷缓存要单独用第三段 C 那个设计去测。
