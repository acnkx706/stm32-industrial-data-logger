# EXP-02b 第一段两臂结论：942 ms 在 20 万次写里没有复现

> 日期：2026-11-06 13:10
> 固件：`Objects/app_fast100k.bin`（70,288 B，Code=66288 RO=3932 RW=616 ZI=18600）
> 两臂各自的细节：`arm_placeholder_result.md`、`arm_realwrite_result.md`
> 原始日志：`placeholder_100k.log`、`realwrite_100k.log`（本地保留，不入库）

## 一、结论

**在两个不同的"91.5% 占用"重建条件下，各跑 100,000 次写，一次 ≥256 ms 都没有出现。**
最坏一笔 72.07 ms。

| 臂 | 怎么把卡弄到 91.5% | 占用 | n | `f_write` 平均 | `f_write` max | `f_sync` max | ≥100 ms | ≥256 ms |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 占位 | `fsutil` 瞬时分配 1.558 GB（不写数据） | 91.57% | 100,000 | 3.63 ms | 72.07 ms | 48.93 ms | 0 | **0** |
| 真写 | 真实写 1.48 GB（163.7 s，9.3 MB/s） | 91.50% | 100,000 | 3.64 ms | 67.19 ms | 51.16 ms | 0 | **0** |

两臂的条件差别只有"填卡的方式"，其它（固件、文件、追加写、启动流程、判读口径）完全相同。
结果几乎一模一样，**说明"占位还是真写"这件事对写延迟没有可测的影响**。

## 二、为什么这足以否掉"1/万"这个量级

原事件是一次 10k 轮里出现 1 次 942 ms。照那个样本算，发生率约 1/10,000。

如果真实发生率真是 1/10,000，那么这次连跑 200,000 次、
一次都不出现的概率是：

```
(1 - 1e-4) ^ 200000 ≈ e^(-20) ≈ 2 × 10^-9
```

**两亿分之一的概率。** 所以：

- **942 ms 不是这张卡在 91.5% 占用下的稳态性质。**
- 它要么是一次极其罕见的事件（发生率远低于 1/10⁴），
  要么是那一次实验的环境里有某个我们没复现出来的因素。

这句话可以放心写进报告；"942 ms 已解决"不能写。

## 三、那一次的环境和这次差在哪

能确定的差别只有一条：**那次卡是从 PC 上直接拔下来的，没有刷卷缓存。**

- 那次：`fsutil` 建完 1.558 GB（10:29:28）→ 没做 `Write-VolumeCache` → 卡被拔走插到板子上。
- 这次：建完/写完之后都做了 `Write-VolumeCache`，再走 Windows 的安全弹出。

后果是那次板子 mount 到的是一个 **FSInfo 说 1.88 GB 可用、实际只有 385 MB** 的文件系统
（这一点今天又原样复现了两次：占位臂 `free_KB=1,825,184`、真写臂 `free_KB=1,775,200`，
而实际可用 336 MB）。FatFs 分配簇靠扫 FAT，所以分配本身是安全的，
但"卡在 PC 侧还有没落完的活"这个状态，这次的两次实验都没造出来。

**这条差别没法在不故意破坏缓存一致性的前提下复现**，所以到此为止，
不再为它专门设计实验。写报告时按"未能复现的环境差异"记一笔即可。

## 四、还有一个可能的解释没排除：不是卡慢，是测量窗口被抢占

`Exp02_Lat` 用的是 `DWT->CYCCNT` 量墙上时间，**窗口里只要有别的任务跑，就会算进去**。

全速模式下 `task_SD` 和 `task_DISP` 都是优先级 1，是**同优先级时间片轮转**，不是独占。
所以一次 `f_write` 的计时窗口里完全可能塞进 OLED 刷新（实测单帧最慢 122 ms）。

支持这条的证据：

- 全程 66 万次计时窗口里，唯一大量出现 ≥100 ms 的是**生产路径 11k 那轮**（225 次 ≥100 ms），
  而那一轮正是任务抢占最严重的；全速模式两臂 20 万次里 ≥100 ms 是 **0 次**。
- 反过来的证据：这两臂里 DISP 任务照样在跑（静音只是不打印，不是不刷新），
  却没有出现 942 ms —— 所以"被 DISP 抢占"单独解释不了 942 ms，
  除非那时 DISP 恰好连续慢了好几帧。

**结论：三个候选（卡内 GC 块合并 / 未刷卷的残留状态 / 计时窗口被抢占）都没被证明。**
报告里必须写成"未定案"，不许挑一个顺眼的当结论。

## 五、这一轮顺带确认的两件事

1. **`f_getfree()` 的 `free_KB` 第三次骗人**：板子报 1.74 GB 可用，实际 336 MB。
   以后这行只当"板子自己以为的"，判填充率只认 PC 侧 `Get-Volume`。
2. **样本数与卡上真实增长对得上**：占位臂跑完，`EXP02.BIN` 正好 +51,200,000 B
   = 100,000 × 512 B。这比 `f_write` 返回 OK 硬。

## 六、这批数据能引用的与不能引用的

能引用：

- 91.5% 占用下，20 万次 `f_write` 平均 3.63~3.64 ms、max 67~72 ms。
- 同一条件下 ≥100 ms 的次数为 **0**。
- 占位与真写两种填卡方式对延迟无可测影响。

不能引用：

- **分位数**。直方图桶是 `uint16`（上限 65,535），n=100,000 时约 19% 样本饱和丢失，
  所以 `p50/p90/p99` 全是假数，只有 `avg` 和 `max` 可信。
- "942 ms 已解决"。
- "卡是健康的"。这张卡有 845 条丢失簇、根目录重名条目、1601 年时间戳，
  健康判定要等第三段的全卡读写校验（`card_stress_test.py`）。
