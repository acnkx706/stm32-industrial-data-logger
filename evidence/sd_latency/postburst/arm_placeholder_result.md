# A-占位臂结果：91.57% 占用 + fsutil 瞬时占位后立刻跑 100k

> 时间：2026-11-06 12:21 占位 → 12:22 起跑 → 12:35 前后结束
> 固件：`Objects/app_fast100k.bin`（70,288 B，Code=66288 RO=3932 RW=616 ZI=18600）
> 原始日志：`placeholder_100k.log`（38,339 B，本地保留，不入库）
> 解析产物：`arm_placeholder/latency_summary.csv`、`latency_top.csv`、`latency_hist.csv`

---

## 一、结论先说

| 项目 | 结果 |
|---|---|
| **942 ms 有没有复现** | **没有**。10 万次里一次 ≥256 ms 都没有 |
| `f_write` | n=100,000，平均 **3.63 ms**，max **72.07 ms** |
| `f_sync` | n=100,000，平均 **3.77 ms**，max **48.93 ms** |
| 最慢那一笔在什么时候 | 开机后 **15.25 秒**（mount/open 之后的第一批写） |
| 占位方式 | `fsutil file createnew`，与原事件同一种做法 |

**能说的**：在"91.57% 占用 + 瞬时占位 1.558 GB"这个条件下，10 万次写没有出现 942 ms
这个量级的事件，最坏只有 72 ms。

**不能说的**：不能说 942 ms "已经解决"或"不存在"。这只说明**在这一次 100k 里没复现**。
原事件仍然是一次孤立观测。

## 二、和原事件的条件对照

| 条件 | 原事件（10:29 那次） | 本次 |
|---|---|---|
| 占用率 | 91.54% | **91.57%** |
| 占位方式 | `fsutil file createnew 1,557,999,387` | 完全相同 |
| 占位到起跑的间隔 | 约 5~7 分钟 | 约 1~2 分钟 |
| 样本数 | 10,000 | **100,000**（覆盖 0~12.5 分钟） |
| 卡有没有刷卷 | **没有**（拔卡时 Windows 缓存里还有东西） | **有**（`Write-VolumeCache` + 安全弹出） |
| 结果 | 1 次 942.3 ms | 0 次 ≥256 ms，max 72.07 ms |

**最后一行那个差别是本次实验最大的遗憾**：这次卡是"干净拔出"的，上一次不是。
所以这两轮的差异里，混着"缓存没刷干净"这个可能因素，不能干净地归因。
下一条（A-真写臂）用真实写入代替 fsutil，就是为了把这个因素单独拿掉。

## 三、时间分布（本次唯一能拿到的"什么时候"证据）

`TOP` 行带 `xTaskGetTickCount()`，最慢的 32 笔分布如下（tick 单位 ms，开机起算）：

| 名次 | 类型 | 耗时 | 开机 tick | 折算 |
|---:|---|---:|---:|---:|
| 1 | write | 72.07 ms | 15,253 | 15.3 s（第一笔附近） |
| 2 | sync | 48.93 ms | 255,067 | 4 分 15 秒 |
| 3 | write | 47.85 ms | 163,076 | 2 分 43 秒 |
| 4 | sync | 46.76 ms | 46,334 | 46 秒 |
| 5 | sync | 45.52 ms | 632,297 | 10 分 32 秒 |
| 6 | sync | 44.94 ms | 397,943 | 6 分 38 秒 |
| 7 | write | 44.47 ms | 515,183 | 8 分 35 秒 |
| 8 | sync | 44.13 ms | 749,912 | 12 分 30 秒（接近收尾） |

**除第一名以外，其余慢样本均匀撒在 12 分钟里，没有在"占位后头几分钟"聚堆。**
这削弱了"占位后立刻 GC"这个解释：如果真是占位触发的 GC，慢样本应该在头几分钟密集出现。

第一名落在 15.25 秒（就是 mount/open 之后的第一批写）这个位置，
更像**冷启动**（第一次访问这块介质）而不是 GC —— 这正是 EXP-02b 第三节 C 要单独测的东西。

## 四、分位数这次不能引用

`latency_summary.csv` 里 `p90=256`、`p99=256` 是**假数**：

- 直方图每个桶是 `uint16`，上限 65,535；
- 这次 n=100,000，3 ms 那个桶被撑满，剩下的样本溢到别处，
  桶和只有 80,556（write）/ 81,912（sync），**丢了约 19%**；
- 所以只有 `avg` 和 `max` 可信，**p50/p90/p99 一个字都不能引**。

要拿分位数，得把桶改成 `uint32`（RAM 从 2×256×2=1 KB 涨到 2 KB，现在 RAM 只剩 1,264 B，
放不下），或者分段 dump 后累加。这次没做，记在这里免得以后误引。

## 五、附带确认：板子的 `free_KB` 又一次骗人

这一轮板子打印 `EXP02,FAST,free_KB=1825184`（= 1.74 GB 可用），
而 PC 侧实际是 **333 MB 可用、91.57% 占用**。

这是第二次复现同一现象，说明它不是偶发：**`f_getfree()` 读的是 FAT32 FSInfo 缓存，
PC 侧写过大文件后它不会更新**。所以 `free_KB` 这行以后只当"板子自己以为的"，
绝不当证据。判填充率只认 PC 侧 `Get-Volume`。
