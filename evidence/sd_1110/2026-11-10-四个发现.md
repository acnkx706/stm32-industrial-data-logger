# 2026-11-10 复盘：四个发现

> 全部在 ver 76-dbg2 上实测。数据文件：`evidence/sd_1110/*.log`、卡上 `261110xx.CSV`。

---

## 1. 串口锁从建的那天起就没生效

**现象**：串口偶尔出现两个任务的输出互相插进对方字节流中间。

```
IDLE: 659/1000 ms  hook 756/s  blank SD: c0
ache restored 1 batch (left=81)
SD: cache restored 1 batch (lREC,seq<3248>,...
```

**根因**：

```c
/* FreeRTOS/include/FreeRTOSConfig.h:151 */
#define configTOTAL_HEAP_SIZE   ((size_t)(64))

/* Hardware/Serial.c:78（改前） */
s_ser_lock = xSemaphoreCreateMutex();   /* 控制块约 80 B > 堆 64 B */
```

`pvPortMalloc` 失败 ⇒ 句柄恒为 NULL ⇒ `Serial_Printf` 里 `if (s_ser_lock != NULL)` 整块跳过 ⇒ 无锁逐字节发（220 B ≈ 19 ms）⇒ 被抢占就插队。

**修法**：改静态，与 `s_i2c_lock` 同一套写法。

```c
static StaticSemaphore_t s_ser_cb;
s_ser_lock = xSemaphoreCreateMutexStatic(&s_ser_cb);
```

**实测对比**：

| | 窗口 | 行数 | 撕裂 |
|---|---:|---:|---:|
| 修前 | 18 s | ~300 | 2 |
| 修后 | 50 min | 51,904 | **0** |

**代价**：ZI 16,092 → 16,172（+80 B）；Code 67,312 → 66,608（−704 B，动态创建路径被丢弃）。

## 2. FAT 文件时间戳写的是 UTC

**现象**：文件名 `26111001`，修改时间却是 `11-09 16:00`（差 8 小时）。

**根因**：文件名用 `MyRTC_GetLocalDateTime()`（`task_sd.c:920`），而 FAT 目录项时间用
`get_fattime()` → `MyRTC_GetDateTime()`（UTC，`diskio_spi.c:216`）。FAT 没有时区字段，
Windows 直接把数字当本地时间显示。

**修法**：`get_fattime()` 改用 `MyRTC_GetLocalDateTime()`。

**实测验证**（修后首次写入）：

| 文件 | 修改时间 | 判定 |
|---|---|---|
| `26111001.CSV` | 11-10 **12:25:36** | 写入时刻，正确 |
| `26111090.CSV` | 11-10 **12:23:44** | 写入时刻，正确 |
| `26110901.CSV` | 11-09 16:00 | 改之前写的，仍是 UTC，符合预期 |

**影响面**：`sd_space_check()` 删最旧逻辑解析的是**文件名**（`sd_find_oldest` 用 `s_fno.fname`），
不看 `fdate`，所以此改动不影响任何逻辑，只影响 PC 上看到的时间。

## 3. 满环回写实测

**实验**：卡拔出，缓存从 0 攒到满（7,616 批），然后插卡回写。

| 项 | 值 | 来源 |
|---|---|---|
| 写满耗时 | **7 h 49 min**（01:19:31 → 09:05:05） | `# SD_REPLAY` 的 rtc 区间 |
| 回写批数 | **7,616** | `SD: replay done` |
| 回写条数 | **27,935** | 同上 |
| 回写耗时 | **72.1 分钟**（4,326 s） | 09:06:57 → 10:19:02 |
| 回写速率 | **1.76 批/秒 = 6.46 条/秒** | 计算 |
| `BAD CACHE ITEM` | **0 次** | 整环 1,904 扇区全擦过一遍 |
| 覆盖速率 | 每 12~13 秒 `ovr +4` | 一个扇区 4 槽，擦前一起作废 |

`ovr` 一次跳 4 而不是 1，原因是 `golden.c:794` 的“进新扇区先擦”会把扇区里剩余有效项一并作废。

**回写速度受循环结构限速**：`task_SD` 每轮只搬一批缓存，然后卡在 `xQueueReceive(..., 1000ms)`。
一次 `f_write` 只要 15.5 ms，理论上每轮能搬几十批。**未改**，只记录。

## 4. 每批条数：今天 5.72，昨晚 3.67 —— 未解释

**今天的分布**（603 个样本，约 50 分钟）：

| n | 次数 | 占比 |
|---:|---:|---:|
| 6 | 503 | 83.4% |
| 5 | 83 | 13.8% |
| 1 | 17 | 2.8% |

平均 **5.72 条/批**，`len` 平均 479 B。与 `golden.c:1795` 的“5.7 条/批”一致。

**触发原因**（`why=` 判断）：

| why | 次数 | n |
|---|---:|---|
| timeout（5 s 超时） | 586（97%） | 6 为主 |
| full（装满 512 B） | 17（3%） | 全部 n=5、len=512 |

**昨晚反推 3.67**：`# SD_REPLAY,batches=7616,recs=27935,rtc=1794244771-1794272705`，
rtc 区间证明环里**全部是当晚 01:19~09:05 的数据**，没有旧批次混入。

**今天顺带修掉的小 bug**：`Sd_DsPush()` 装满刷分支没复位 `s_ds_t0` ⇒ 下一条进来时起点还是旧的
⇒ 100 ms 后巡检判“已超 5 秒” ⇒ 单条成批。实测 **17 次 full 全部紧跟一个 n=1**，一一对应。

该 bug 只解释 2.8% 的槽浪费，**解释不了 3.67**。

**待定案**：新增 `stall` 计数（一批 <4 条则 +1），打在 `drained` 行末尾。
今晚再挂一次通宵，明早看 `stall` 涨速即可判断“RAW 记录流停顿”是不是元凶。
