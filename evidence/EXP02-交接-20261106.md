### 丢条量随停摆时长怎么长

采样 10 Hz，一块 512 B 缓冲装 5 条 = 0.5 s，两块 = 1.0 s。

| 停摆 | 每次平均丢条 | 折算时间 | 被吸收的时长 |
|---|---:|---:|---:|
| 100 ms | 0 | 0 ms | 100 ms |
| 250 ms | 0 | 0 ms | 250 ms |
| 500 ms | 约 1 | 约 100 ms | 约 400 ms |
| 1000 ms | 5.8 | 约 580 ms | 约 420 ms |
| 2000 ms | 15.7 | 约 1570 ms | 约 430 ms |

**可吸收 400~430 ms，超过之后每多停 1 秒稳定多丢 10 条。**
这个线性关系比"临界点 500 ms"这种说法有用得多。

## 五、日志格式速查

**停摆试验行**（15 个字段）：

```
EXP02,<kind>,<ms>,<qlen>,<trial>,<qmax>,<Δqfull>,<Δq_full>,<Δno_buf>,<Δenq_fail>,<Δacq_late>,<first_reason>,<first_ms>,<acq_a>,<acq_b>,<sd_err>
```

- `kind`：0 = 停 SD 任务，1 = 停 PROC 任务
- `first_reason`：0=`LOSS_Q_FULL`，1=`LOSS_NO_BUF`，2=`LOSS_ENQ_FAIL`，5=`LOSS_ACQ_LATE`，**255 = 全程没丢**
- `first_ms`：从武装到第一次丢条的毫秒数（不是停摆时长）
- `trial` ≥ 101 的是连停模式，其余是矩阵模式

**延迟行**：

```
LAT,SUM,<op>,<n>,<avg_us>,<max_us>,<ovf>      op 0=write 1=sync；ovf=掉进 >=256ms 桶的个数
LAT,OVF,<op>,<n>,<idx>,<tick>                 第一次 >=256ms 的样本序号与开机 tick（2026-11-06 新增）
LAT,<op>,<bin>,<count>                        bin 0..255，单位 ms，bin 255 表示 >=255
TOP,<op>,<us>,<tick>                          最慢的 32 次，tick 就是时间轴
```

**注意**：直方图计数是 `uint16`，**超过 65,535 次就饱和**。所以 n > 65,535 的轮次
（比如 100k）**分位数全部无效**，只能引用 `avg` 和 `max`。
10k 及以下的轮次桶和是满的，分位数可信 —— 引分位数前先看 `latency_summary.csv` 的 `hist_sum` 等不等于 `n`。

**STAT 行**（正式固件每 10 秒一行）：

```
STAT acq=600 proc=600 full=0 qmax=1 drop=0 i2c=1450 i2c_max=15561 sd_err=0 sd_last=0 sdstk=146
```

判据：`acq==proc` 不积压、`full==0`、`drop==0`、`sd_err==0`、`sdstk` 不低于 146。
`i2c_max` 开机后常见 15554~15561 µs（历史值 2650~2736），只出现一次且不再涨，**记作待观察**。

## 八、七个坑（都是实际踩过的，别再踩）

1. **`--no-build` + 陈旧 axf**：一度反复烧同一个旧镜像（70,380 B 的擦卡版），
   表现为"每次烧完都卡在同一处"。真因不是硬件。**规矩：编译 → fromelf → 核对 bin 时间戳与大小 → 才烧**。
2. **板子报的 `free_KB` 不可信**：`f_getfree()` 读 FAT32 的 FSInfo 缓存。
   PC 侧写过 1.558 GB 之后，板子仍报 1.88 GB 可用，于是整批实验被误判成"约 50% 填充"，
   实际是 91.5%。**规矩：填充率只认 PC 侧读到的卷信息。**
3. **串口行交叠**：`REC,` / `SONAR` / `DISP:` 会插进 `EXP02` / `LAT` 行中间。
   解析器必须用严格正则，坏行直接丢。已丢的例子：q500 第 12 行、100k 的 `f_write` 汇总行。
4. **直方图 `uint16` 饱和**：单桶上限 65,535。n 超过它就**没有分位数**，只有 avg/max。
5. **IWDG 6.55 s**：只在 idle 钩子里喂狗。全速循环占满 CPU 会复位；
   现在的做法是每 64 次 `IWDG_ReloadCounter()` + `taskYIELD()`。
6. **RAM 只剩约 1.3 KB**：测试固件 ZI 18,596 + RW 596。曾经因为加了板子端擦卡/填充代码，
   ZI 顶到 19,660，栈只剩 224 B，App 起不来。**不要在板子上加大缓冲**。
7. **不许手改 `.uvprojx`**：新 `.c` 用 `#include` 进 `freertos_demo.c`。
   `exp02.c` 必须放在 `Stat_t g_stat;` **之后**（它要引用），放前面会编译不过。

另外两条工程约定：`.gitattributes` 统一 `text eol=crlf`；
串口 COM12 @115200 会被 Keil 的 UART 窗口、桌面上的「串口助手」、上一轮残留的 python 抢占，
抓包前先 `Get-Process -Name UV4,python -ErrorAction SilentlyContinue` 确认。

### 第八节的补充（2026-11-06 14:05，EXP-02b 踩出来的三条）

8. **`free_KB` 不可信这件事要收窄范围**：在"格式化后干净卸载"的卡上它是**准的**
   （实测 `3,863,936 KB` 与实际一致）。它只在"PC 侧写过东西但没刷盘就拔卡"时才错。
   **规矩：报填充率时同时说清卡是怎么离开 PC 的。**
9. **两个测试固件的 Code 与文件大小可以完全相同**：`app_fast10k.bin` 与 `app_fast100k.bin`
   都是 70,288 B、Code=66288，因为差别只是一个立即数。
   **规矩：靠文件名 + 板上打印的 `n=10000`/`n=100000` 双确认，别只看大小。**
10. **串口交叠要从源头治，不是在 PC 侧容错**：新增的 `g_print_quiet` 在全速跑批期间
   压掉 `IDLE:`/`SONAR:`/`DISP:` 三类周期打印（计数照常推进，只跳打印），
    100k 的两行 `LAT,SUM` 从此都完整。
    **注意 `f_open` 失败那条早退路径也必须解除静音**，否则没插卡时整板永久闭嘴，看起来像卡死。
11. **`eject` 会偶发失败**：刚写完 3.9 GB 时调 Shell 的 `Eject` 动词可能不生效
    （卷还忙）。等几秒重试一次即可；**「`E:` 还在不在」必须自己验，不能假定弹出成功**。

## 九、这个实验不能证明什么

- **注入的停摆不是"卡内部 busy"**：它是让 `task_SD` 主动 `vTaskDelay`。
  它验证的是缓冲链的计数器归属，**不是真实卡的写失败行为**。
- **只有一张卡、一个批次**。换卡、卡老化、极端温度完全没测。
  卡在介质层面是健康的（全容量写满+拔插+读回，0 坏块），但"健康"只等于"本次覆盖范围内可读写"。
- **填充率有三个点（0% / 52% / 91.5%），但不是干净对照**：
  0% 是格式化后的干净卡，52% 与 91.5% 是格式化前的脏卡（含 845 条丢失簇）。
  **占用率和卡状态两个变量同时变了，这一轮设计分不开它们。**
  另外 0% 与 52% 各只有 1 万次样本，尾部比 91.5% 那两个 10 万次弱。
- **942 ms 那一次不能归因，也没能复现**：它在 10:36 出现一次（10k 样本），
  此后两臂各 10 万次（占位 / 真写）一次 ≥256 ms 都没有。
  按 1/10⁴ 的发生率算，20 万次零出现的概率约 2×10⁻⁹，所以它不是稳态性质；
  但"已解决"三个字不能写。三个候选（卡内 GC / 未刷卷的残留状态 / 计时窗口被抢占）都没证明。
- **长尾只到 1/10 万**（100k 样本）。1/百万量级没覆盖。
- **分位数基本不可用**：直方图桶是 `uint16`，n>65,535 就饱和。
  只有 0% 那轮（n=10,000）的分位数可信。
- **停摆时长只测到 2 s**，2 s 以上没有数据。
- 没有做"停摆时长随机、相位随机"的长时间注入，给不出真实工况下的年化丢条期望。

## 十一、给下一个 AI 的硬规则

这个用户对"没证明的结论"极其敏感，下面几条踩过就知道疼：

1. **不许在板子上做填充/擦卡/批量写**。卡上的准备全部在 PC 侧做完并校验。原话：
   「该在能在电脑上搞好的就在电脑上搞好」。
2. **不许动 EXP-01 的 1.36 GB 原始数据**。那是别人 17 天账本结论的唯一凭证。
3. **先说数据、再说结论**。数字必须标来源（哪份日志、哪天测的、n 多少）。
   做不到的地方就明写"不能证明"，不要用"应该""大概"糊过去。
4. **改代码要把原文贴给他**：改动处的**改之前 / 改之后**两段真实代码，
   外加"为什么这么写 / 不这么写会怎样 / 怎么验证"。他是学生，读代码是主要学习途径。
5. **注释规范**（`stm32/学习笔记/64-代码注释规范-2026-11-03.md`）：
   不许把 `✗ ✓ ★` 当标点用、注释里不许出现 Markdown、长注释分四段
   （做了什么 / 为什么 / 影响什么 / 怎么验证）、每段不超过 4 行、数字必须标来源。
6. **简单的事不要问**（编译、烧录、抓包这种直接做）；**要动手/有破坏性的先问**。
7. 提交推送：`git add -A` → 中文 commit message 写清"改了什么 + 数字结果 + 更正了什么" → `git push origin HEAD`。
   交接时 `main` 与 `origin/main` 同步，工作区干净。
